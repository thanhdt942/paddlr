# Contributing to Paddlr

Thank you for your interest in contributing to Paddlr! We are committed to building an open, maintainable, and agent-agnostic software engineering framework.

Please read our [Code of Conduct](CODE_OF_CONDUCT.md) and review the [Universal Agent Operating Instructions](rules/AGENTS.md) before contributing.

---

## 1. Principles of Contribution

All contributions must honor the core tenets of Paddlr:

1. **Independent:** Do not couple the framework to proprietary or single-vendor frameworks.
2. **Agent-Agnostic:** Keep the core engineering methodology portable across coding agents (Antigravity, Claude Code, OpenCode, Codex).
3. **Portable-First:** Use the open Agent Skills format. Rely on Markdown, standard repository artifacts, and optional deterministic Python standard library utilities.
4. **Minimal Overhead:** Do not introduce unnecessary abstractions, dependencies, databases, or runtime daemons.
5. **Evidence-Based:** Validate every skill, workflow, or adapter with reproducible test evidence.

---

## 2. Contribution Categories

You can contribute in several areas:

- **Skills (`skills/`):** The cohesive Agent Skills (`feature-development`, `writing-specs`, `writing-plans`, `test-driven-development`, `sre-debugging`, `code-review`, `release-management`, `skill-creator`) and their specialized progressive disclosure references in `skills/<name>/references/`.
- **Project Knowledge (`docs/paddlr/`):** Guidelines and tooling for canonical persistent repository knowledge.
- **Commands (`commands/`):** Claude Code slash command definitions with `/pdl:` prefix.
- **OpenCode Plugin (`index.js`, `.opencode/`):** OpenCode tools, lifecycle hooks, and TypeScript bindings.

---

## 3. Skill Authoring Contract

Every Skill resides in its own directory under `skills/<skill-name>/` with a mandatory `SKILL.md`:

```text
skills/<skill-name>/
├── SKILL.md          # Concise entrypoint
├── references/       # Modular progressive disclosure methodology guides
├── scripts/          # Optional deterministic helper scripts
└── assets/           # Optional assets/diagrams
```

---

## 4. Local Validation & Quality Checks

Before submitting a pull request, run the framework validation suite locally:

```bash
# 1. Validate all Agent Skills format and contracts
python scripts/validate_skills.py --verbose

# 2. Run complete automated test suite
python -m unittest discover -s tests -v
```

---

## 5. Development & Pull Request Process

1. **Check Issues & Discussions:** Before starting substantial work, review existing issues or open a proposal to align on design.
2. **Branch from `dev`:** Create a descriptive branch from `dev` (e.g., `feat/add-new-skill`, `fix/skill-validator-link-check`) and open the pull request against `dev`. The default `release` branch is generated by the release workflow and never accepts direct changes.
3. **Keep Changes Focused:** Implement one logical feature or skill per pull request.
4. **Follow AGENTS.md Guardrails:** Never make unapproved commits or run destructive Git commands.
5. **Write Conventional Commits:** Format every commit message as described in [Commit Message Convention](#commit-message-convention).
6. **Submit Pull Request:** Use the [Pull Request Template](.github/pull_request_template.md) and attach captured test execution output.
7. **Maintainer Review:** Pull requests are reviewed by maintainers against the [Universal Agent Instructions](rules/AGENTS.md) and design principles.

### Commit Message Convention

Commits follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

```text
<type>[(scope)][!]: <description>

[optional body]

[optional footer(s)]
```

| Type | Use for | SemVer |
|---|---|---|
| `feat` | New capability | MINOR |
| `fix` | Bug fix | PATCH |
| `docs`, `test`, `refactor`, `perf`, `style`, `build`, `ci`, `chore` | Other changes | none |

- **Breaking change:** append `!` after the type/scope, or add a `BREAKING CHANGE: <description>` footer (any type; MAJOR).
- **Scope** (optional): the affected area in parentheses, e.g. `skills`, `core`, `plugins`, `packaging`, `release`.
- **Footers** use git trailer format, e.g. `Refs: #12`.
