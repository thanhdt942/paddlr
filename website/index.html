Paddlr Simple on the Surface. Sophisticated Underneath.

Disciplined software engineering for AI coding agents.

Paddlr is an open-source, agent-agnostic engineering framework that equips your AI coding agent with reusable skills for specifications, contract-first planning, Test-Driven Development, scientific debugging, and Git-tracked project memory.

Why Paddlr

Handle the complexity. Simplify the experience.

Unstructured agent prompting breaks down on real codebases: agents edit files before inspecting conventions, store plans in ephemeral chat threads, guess fixes without isolating root causes, and report completion without running verification.

The Problem

Ad-hoc prompts don't scale

Repeating long procedural prompts in every session leads to inconsistent quality, forgotten architectural decisions, and fragile edits across multi-file features.

Why Paddlr Exists

Codified engineering habits

Paddlr packages proven engineering workflows—spec authoring, contract-first task decomposition, iron-law TDD, and SRE debugging—into standard, reusable Agent Skills.

Key Differentiator

Git-tracked project memory

Instead of losing context when a chat window closes, Paddlr persists specs, per-request implementation plans, and immutable ADRs directly in docs/paddlr/.

Above the Surface

Calm, frictionless developer workflow

Like a duck gliding across water, the day-to-day interface stays effortless: one plugin install, automatic session bootstrap, and intuitive /pdl:* slash commands.

  • Zero memorization of sprawling checklists
  • Proportional process: small fixes stay fast (Level 1)
  • Identical skills and commands across 4 coding agents
Below the Surface

Rigorous, verifiable engineering discipline

Underneath the simple command surface, Paddlr coordinates quality gates and deterministic artifacts at every phase of development.

  • Mandatory codebase inspection before modifying files
  • Contract-first plans (Consumes / Produces) & TDD cycles
  • Concrete verification statuses (PASS, FAIL, BLOCKED)
What Paddlr Is What Paddlr Is Not
A collection of 8 reusable AI Agent Skills conforming to the Agent Skills open standard Not a standalone AI coding agent or LLM provider
A practical Software Engineering Framework with rules, lifecycle hooks, scanner scripts, and tests Not an IDE or closed proprietary platform
A system for producing checkable engineering artifacts in docs/paddlr/ Not a loose list of copy-paste prompt snippets
Agent-agnostic by design across Claude Code, Antigravity, OpenCode, and Codex Not locked into a single vendor ecosystem

Core Features

Everything required for disciplined AI engineering.

Every capability in Paddlr is implemented as verifiable files, skills, hooks, and scripts in the repository.

Primary Capability · Skills & Project Memory

8 Composable Agent Skills with Git-Tracked Memory

Paddlr orchestrates end-to-end engineering through eight modular skills under skills/*/SKILL.md and persists every specification, contract-first plan, and architectural decision in docs/paddlr/.

  • Always-new plan per request: Creates a dedicated file in docs/paddlr/plans/YYYY-MM-DD-<feature>.md without overwriting history.
  • Immutable ADRs: Architectural decisions live in docs/paddlr/decisions/XXXX-<slug>.md and are indexed in DECISIONS.md.
  • Progressive disclosure: Skills load detailed references/ only at the phase where they are needed.

├── decisions/   # Granular immutable ADRs

Safety Guardrail · index.js & rules/AGENTS.md

Destructive Git & Execution Guardrails

Binds strict operational rules forbidding unapproved commits or destructive Git operations, enforced at runtime in OpenCode via the tool.execute.before hook.

blocked commands (tool.execute.before) 
git reset --hard   # Blocked without explicit user confirmation
git clean -fd      # Blocked by [Paddlr Guardrail]
git push --force   # Blocked by rules/AGENTS.md

How It Works

Five steps from requirement to verified code.

Paddlr guides your coding agent through a predictable engineering loop where each stage produces concrete, inspectable evidence.

STEP 01

Understand

Inspect Git status, repository layout, tech stack, and test runners before touching any application file.

python scripts/scan_repo.py .
STEP 02

Analyze & Plan

Clarify requirements, draft a specification, and decompose work into contract-first tasks.

/pdl:writing-specs
/pdl:writing-plans
STEP 03

Implement

Execute one small slice at a time strictly test-first: write a failing test, make it pass, then refactor.

/pdl:test-driven-development
STEP 04

Evidence Verify

Run tests and linters to capture PASS/FAIL evidence, debug failures scientifically, and review diffs.

/pdl:code-review
/pdl:sre-debugging
STEP 05

Finalize

Record completed slices in project memory and execute governed semantic releases when ready.

/pdl:release-management

Installation

Paddlr ships native manifests at the repository root for all four supported coding agents. Use the Agent Installation Hub above to copy interactive commands, or reference the manifest mapping below:

  • Claude Code: .claude-plugin/plugin.json, .claude-plugin/marketplace.json, and hooks/hooks.json.
  • Google Antigravity (agy): plugin.json and hooks.json.
  • OpenCode (v1 & v2): package.json, index.js, index.d.ts, and .opencode/INSTALL.md.
  • OpenAI Codex (codex): .codex-plugin/plugin.json and .agents/plugins/marketplace.json.

Configuration & Project Memory

Paddlr uses rules/AGENTS.md as its binding operational rulebook (and rules/CLAUDE.md as the Claude Code router that imports @AGENTS.md). Project artifacts are stored canonically under docs/paddlr/:

text 
docs/paddlr/
├── specs/          # Feature specifications (YYYY-MM-DD-<feature>.md)
├── plans/          # Dedicated implementation plan per request (YYYY-MM-DD-<feature>.md)
├── decisions/      # Individual immutable ADRs (XXXX-<slug>.md)
├── DECISIONS.md    # ADR index
├── PROGRESS.md     # Current operational status & completed slices
└── PLAN.md         # Long-term engineering roadmap
Legacy path fallback: OpenCode's pdl_status tool inspects docs/paddlr/ first and automatically falls back to legacy docs/hsiw/, .pdl/, or .hsiw/ directories if present.

Usage & Workflow Levels

Paddlr classifies every engineering task into one of three risk levels before writing code, ensuring verification evidence is always reported using standard statuses (PASS, FAIL, BLOCKED, NOT RUN, NOT APPLICABLE):

  • Level 1 (Small Change): Typo fixes, minor refactoring, localized bugs. No formal spec or plan required.
  • Level 2 (Feature Development): Multi-component features. Requires a specification in docs/paddlr/specs/ and a fresh implementation plan in docs/paddlr/plans/.
  • Level 3 (Architectural Change): High-impact design trade-offs or breaking changes. Requires an ADR in docs/paddlr/decisions/ and explicit user approval before implementation.

Slash Commands Reference

All eight slash commands are defined in commands/*.md and invoke their corresponding skill in skills/:

Command Arguments Description
/pdl:feature-development [feature idea, requirement, or user story] Orchestrate end-to-end feature delivery from intake to verified completion
/pdl:writing-specs [feature idea or requirements] Turn requirements into a clear, reviewable specification in docs/paddlr/specs/
/pdl:writing-plans [spec path or feature description] Create a bite-sized, contract-first implementation plan in docs/paddlr/plans/
/pdl:test-driven-development [task or behavior to implement] Implement code strictly test-first (RED → GREEN → REFACTOR)
/pdl:sre-debugging [error message, failing test, or symptom] Evidence-based root cause analysis and scientific troubleshooting before fixing
/pdl:code-review [commit range, task, or files to review] Perform independent, read-only code review against specifications and quality standards
/pdl:release-management [release type, version bump, or release stage] Manage software release lifecycle and persist conventions in RELEASE.md
/pdl:skill-creator [skill idea, repeated workflow, or skill to audit] Design, draft, verify, and package reusable AI agent skills

Skills, OpenCode Tools & Verification Scripts

In addition to the 8 skills in skills/, Paddlr exposes native tools in OpenCode (pdl_bootstrap, pdl_status, pdl_scan, plus legacy hsiw_* aliases) and standalone Python scripts in scripts/:

bash 
# Validate all 8 skills against the Agent Skills open standard
python scripts/validate_skills.py --verbose

# Run the complete unit & multi-agent plugin test suite
python -m unittest discover -s tests -v

# Check all internal Markdown links across the repository
python scripts/check_markdown_links.py

Customization

Use /pdl:skill-creator to author new custom skills for your team following progressive disclosure (SKILL.md under 500 lines with on-demand references/), then validate them with python scripts/validate_skills.py.

For local OpenCode development or offline workspaces, link Paddlr directly via .opencode/plugins/paddlr.js:

javascript (.opencode/plugins/paddlr.js) 
export { default } from "./path/to/paddlr/index.js";

Troubleshooting

  • OpenCode v1 vs. v2 config key: Use "plugins": [...] in opencode.json for OpenCode v2 (@opencode/plugin) and "plugin": [...] for OpenCode v1 (@opencode-ai/plugin).
  • SessionStart hook not firing: Ensure python3 / python (3.10+) is on your PATH. On Windows, hooks/run-hook.cmd handles cross-platform invocation.
  • Git command blocked in OpenCode: The tool.execute.before hook intentionally blocks unconfirmed git reset --hard, git clean -fd, and git push --force commands per rules/AGENTS.md.
  • pdl_status reports uninitialized repository: Run a Level 2 workflow (such as /pdl:writing-specs) or create docs/paddlr/ to initialize project memory.
FAQ

Frequently Asked Questions

Does Paddlr lock me into a single AI coding agent?

No. Paddlr is agent-agnostic. The exact same skills, rules, and docs/paddlr/ project memory work across Claude Code, Google Antigravity, OpenCode, and OpenAI Codex. See the Agent Compatibility Hub for installation steps.

Do small bug fixes require writing a specification and implementation plan?

No. Paddlr enforces proportional overhead (Usage & Workflow Levels). Level 1 small changes skip formal specs and plans; only Level 2 features and Level 3 architectural changes create spec and plan files in docs/paddlr/.

Does scan_repo.py or pdl_scan expose secrets in .env files?

Never. scripts/scan_repo.py matches sensitive filename patterns (.env*, *secret*, *token*, *credential*, *.pem, *.key, SSH keys) and flags them by filename only without reading their contents.

Why does Paddlr create a new plan file for every request instead of editing one plan?

Overwriting a single scratchpad erases engineering history. Storing each feature plan in docs/paddlr/plans/YYYY-MM-DD-<feature>.md preserves a clean, auditable contract of what was planned and verified (Configuration & Project Memory).
